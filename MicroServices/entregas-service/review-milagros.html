Resumen ejecutivo: la rama implementa un primer CRUD de entregas y el schema está bastante cerca del modelo de datos, pero todavía NO está lista para mergear. Hay que adaptarla a la arquitectura actual: gateway como única entrada HTTP, microservicios por TCP, schema Prisma unificado, JWT/roles y filtro por vendedor. Hoy el servicio expone HTTP + Swagger directo, no tiene TCP, no está conectado al gateway, no tiene tests y lista entregas sin filtrar por el vendedor autenticado.

1. Bloqueantes

P0 La rama está desactualizada contra develop

Qué pasa: la rama nace de d28fffc, antes del merge #19 donde cerramos HTTP directo de usuario-service y dejamos gateway como única entrada.

Por qué bloquea: si se mergea así puede reintroducir controllers HTTP en usuario-service y borrar partes actuales del gateway/docs. Antes de tocar nada funcional hay que actualizar la rama contra origin/develop y resolver conflictos preservando lo actual.

P0 entregas-service no usa TCP

Evidencia: no hay @MessagePattern, no hay Transport.TCP, no hay connectMicroservice() ni módulo TCP. Solo hay controllers HTTP (@Get, @Patch).

Qué esperamos: frontend → gateway HTTP → action registry → TCP hacia microservicio. El MS de entregas no debe exponer endpoints de negocio por HTTP directo.

Qué hacer: crear DeliveriesTcpController, TcpPayloadAdapter y TcpModule siguiendo el patrón de usuario-service/products-service.

P0 Sin autenticación ni filtro por vendedor

Evidencia: findAll(query) solo filtra por fecha. No recibe user context, no valida rol vendedor y no filtra vendedor_id.

Por qué bloquea: el contrato dice: “vendedorId NUNCA viene del body/query. Se extrae del token JWT. Cada vendedor solo ve SUS entregas.” Hoy un vendedor podría ver entregas de otros vendedores si accede al endpoint.

Qué hacer: en TCP, obtener el usuario desde payload, resolver el vendedorId real y filtrar siempre por vendedor_id. En findOne y updateStatus también validar ownership.

P1 HTTP + Swagger directo

Evidencia: main.ts usa NestFactory.create(), app.listen(PORT), SwaggerModule.createDocument() y SwaggerModule.setup('api/docs').

Qué esperamos: después de lo que hicimos en usuario-service, los MS de dominio deben ser TCP-only. Swagger debe vivir en gateway si necesitamos documentación pública.

Qué hacer: sacar Swagger y HTTP de negocio. Si se mantiene GET /health, que sea interno y explícito para Docker, no API de negocio.

P1 No hay tests

Evidencia: no existe ningún *.spec.ts en MicroServices/entregas-service.

Qué hacer: agregar tests mínimos para service, TCP controller, validación de transiciones y ownership por vendedor.

6. Plan de adaptación antes de mergear

  1. Actualizar rama contra origin/develop y resolver conflictos sin reintroducir HTTP en usuario-service ni borrar docs/gateway actuales.
  2. Convertir entregas-service a TCP-only: crear módulo/controller TCP y sacar Swagger/HTTP de negocio.
  3. Implementar payload adapter: validar body/query y extraer user/role del payload enviado por gateway.
  4. Filtrar por vendedor autenticado: list/get/update deben validar vendedor_id. Nada de vendedorId por query/body.
  5. Mover schema al schema unificado: conservar @@map("DELIVERY"), agregar relaciones si corresponde y eliminar migration local separada.
  6. Integrar gateway: action registry, ClientProxy, env vars y docker-compose.
  7. Agregar tests: service, TCP controller, transiciones válidas/inválidas, ownership y paginación.
  8. Eventos: si Kafka queda fuera del scope, documentar que DeliveryStarted/Completed/StatusChanged queda pendiente.

7. Mensaje listo para enviar

Mili, revisamos tu entregas-service. La base de dominio está bien encaminada: tenés el modelo DELIVERY bastante cerca del contrato, las transiciones de estado están pensadas y los DTOs están separados.

Lo que falta es adaptarlo a la arquitectura actual que ya tenemos funcionando:

  • Actualizar tu rama con develop actual antes de mergear, porque quedó anterior al cierre HTTP de usuario-service.
  • Pasar el servicio de HTTP/Swagger a TCP-only. El gateway es la única entrada HTTP.
  • Agregar handlers TCP: deliveries.list, deliveries.get, deliveries.update_status.
  • Filtrar siempre por vendedor autenticado. Cada vendedor solo puede ver/modificar sus entregas.
  • Mover el modelo Prisma al schema unificado. El @@map("DELIVERY") está bien.
  • Conectar gateway: action registry + ClientProxy + docker-compose/envs.
  • Agregar tests mínimos antes de pedir merge.

Con esos cambios queda alineado con gateway y usuario-service.
