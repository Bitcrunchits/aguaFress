1. Bloqueantes P0/P1

P0 La rama está desactualizada y revertiría parte de develop

Qué pasa: la rama nace de d28fffc, antes del merge #19 de gateway-unica-entrada. Si se mergea así, el diff contra develop muestra que volvería a agregar controllers HTTP de usuario-service y removería piezas del gateway/docs que ya están en develop.

Por qué bloquea: esto rompe la decisión arquitectónica ya cerrada: usuario-service TCP-only, gateway como única entrada HTTP.

Qué hacer: rebasear o mergear origin/develop en esta rama y resolver conflictos preservando lo actual de develop. Recién después revisar products-service.

P0 products-service no es TCP-only: levanta HTTP y Swagger

Evidencia: src/main.ts usa NestFactory.create(AppModule), app.listen(port), SwaggerModule.createDocument() y SwaggerModule.setup('api/docs').

Qué esperamos: después de cerrar HTTP en usuario-service, el patrón correcto para microservicios de dominio es TCP-only. El único HTTP público debe ser el gateway.

Qué hacer: quitar Swagger y HTTP directo. Usar NestFactory.createMicroservice() con TCP o mantener HTTP solo si el equipo decide explícitamente un healthcheck interno, nunca como API/documentación de negocio.

P1 No está conectado al gateway

Qué pasa: los handlers TCP existen, pero el gateway mantiene products, categories y brands como status: 'unavailable' y sin acciones.

Impacto: el MS corre aislado, pero el frontend no puede llegarle porque el gateway no sabe enrutar /api/v1/products/list → products.list.

Qué hacer: agregar actions al ACTION_REGISTRY, registrar un ClientProxy TCP hacia products-service:3013, agregar env vars y docker-compose.

P1 El único test falla

Comando: pnpm --filter @agua/products-service test

Resultado: falla pricing.service.spec.ts con error de parser en import { Test, type TestingModule }. Jest no está configurado para TypeScript/ts-jest en este package.

Qué hacer: agregar configuración Jest equivalente a usuario-service/gateway (preset: 'ts-jest', testEnvironment: 'node') y ampliar cobertura.

6. Plan recomendado antes de merge

  1. Actualizar la rama contra origin/develop y resolver conflictos sin reintroducir HTTP en usuario-service.
  2. Convertir products-service a TCP-only: sacar SwaggerModule, app.listen() y HTTP business/docs. Si se mantiene health, que sea decisión explícita e interna.
  3. Mantener schema Prisma propio del MS: products-service debe tener su propio Docker, DB y schema.prisma. Aplicar @db.Uuid, @db.VarChar/@db.Text, @@map UPPERCASE y referencias lógicas por ID, sin FKs Prisma cruzadas a usuario-service.
  4. Integrar con gateway: action registry, ClientProxy TCP, env vars y docker-compose.
  5. Resolver vendedorId correctamente: confirmar si JWT sub es AUTH_USER.id o VENDEDOR.id. Si es AUTH_USER.id, usar resolución contra usuario-service.
  6. Arreglar Jest y agregar tests mínimos: ProductsService, CategoriesService, TCP controllers, PricingService.
  7. Revisar eventos: el contrato dice ProductUpdated/ProductDeleted. Si Kafka queda fuera de alcance, documentarlo como pendiente explícito.
