  • ✅ TcpPayloadAdapter — implementa requireUser(), requireRole(), validación con ValidationPipe. Mismo patrón que usuario-service.

  • ❌ Falta ClientProxy en gateway — no está registrado el ClientsModule hacia products-service:3013.

  • ❌ Swagger en HTTP directo del MS no sirve. usuario-service tenía lo mismo y lo sacamos. La razón: si el objetivo es que todo el tráfico pase por el gateway (TCP), tener Swagger colgado del puerto HTTP 3003 del MS no tiene sentido. El frontend no pega ahí, el gateway no redirige ahí, y Swagger documenta endpoints que solo existen como TCP.

    • 🔴 Mejoras CRÍTICAS (hay que hacerlas sí o sí)

    ÍtemDetalle
    Schema desunificado

    Qué pasa: Tu schema Prisma está en products-service/prisma/schema.prisma, pero el proyecto entero usa un solo schema compartido en usuario-service/prisma/schema.prisma. Ahí viven TODAS las tablas del sistema: AUTH_USER, VENDEDOR, CLIENTE, SUPER_ADMIN, QR_CODE, etc.

    Por qué está mal: Si cada MS tiene su propio schema, Prisma genera migraciones independientes. Terminamos con bases de datos inconsistentes — un MS migra y el otro no, las relaciones entre tablas no existen, los tipos chocan. Ya pasó antes y tuvimos que unificar todo a la fuerza.

    Cómo arreglarlo: Mover los 3 modelos (Categoria, Marca, Producto) al schema central de usuario-service/prisma/schema.prisma. Tu prisma/ local puede quedar vacío o borrarse (el cliente se genera desde el schema unificado igual).
    Sin action registry

    Qué pasa: Tus 8 handlers TCP existen en products-service pero el gateway no sabe que existen. El gateway usa un ACTION_REGISTRY (en gateway/src/actions/action-registry.ts) que mapea nombres de ruta a { service, tcpPort }. Sin entries ahí, el gateway tira 404 aunque el MS esté vivo.

    Por qué está mal: Nadie puede llamar a products.list, products.create, etc. porque el gateway no sabe hacia dónde redirigir. Todo el sistema está diseñado para que el gateway sea la única puerta de entrada.

    Cómo arreglarlo: Agregar 8 entries en action-registry.ts con el formato:
    { route: 'products.list', service: 'products-service', tcpPort: 3013 },
    { route: 'products.create', service: 'products-service', tcpPort: 3013, requireAuth: true },
    etc. Seguir el mismo patrón que las 14 rutas de usuario-service que ya están en el registry.
    TCP sin ClientProxy

    Qué pasa: El gateway no tiene un ClientsModule registrado para conectarse por TCP a products-service. Tiene uno para usuario-service (puerto 3011) pero no para products-service (3013).

    Por qué está mal: El action registry resuelve la ruta, pero sin un ClientProxy configurado, el gateway no puede abrir un socket TCP hacia tu MS. El ClientTCP de NestJS necesita saber host + puerto.

    Cómo arreglarlo: En el módulo del gateway (probablemente gateway/src/app.module.ts o donde esté el ClientsModule.register() de usuario-service):
    ClientsModule.register([{ name: 'PRODUCTS_SERVICE', transport: Transport.TCP, options: { host: 'products-service', port: 3013 } }])
    Y agregar PRODUCTS_SERVICE_TCP_PORT en las env vars del gateway.
    Faltan tests

    Qué pasa: Tenés 1 spec (pricing.service.spec.ts). El proyecto tiene 278+ tests en usuario-service. No podemos mergear un MS sin cobertura.

    Por qué está mal: Sin tests no podemos asegurar que el CRUD funciona, que el ownership check no se pasa, que los filtros traen los datos correctos, que el TCP controller responde bien. Ya nos pasó de mergear cosas que rompían todo y había que revertir.

    Mínimo necesario:
    - products.service.spec.ts: create, findById, update, delete, ownership check (que un vendedor NO pueda modificar producto de otro)
    - products-tcp.controller.spec.ts: cada handler responde con el pattern correcto
    - categories.service.spec.ts: listCategorias y listMarcas filtran por vendedorId
    - rpc-exception.filter.spec.ts: que maneje HTTP y RPC correctamente
    Naming @@map inconsistente

    Qué pasa: Tus tablas se llaman productos, categorias, marcas en la DB (minúscula). El proyecto usa SIEMPRE MAYÚSCULA con guión bajo: AUTH_USER, VENDEDOR, CLIENTE, SUPER_ADMIN, QR_CODE.

    Por qué está mal: Cuando alguien corre queries directo a Postgres, tiene que adivinar el casing. Es un desorden que después nadie quiere limpiar.

    Cómo arreglarlo: Cambiar los @@map a UPPERCASE:
    @@map("CATEGORIA"), @@map("MARCA"), @@map("PRODUCTO")
    El idioma (español/inglés) no está definido — el proyecto mezcla. Lo importante es el UPPERCASE.
    Swagger en HTTP directo

    Qué pasa: Tu main.ts tiene SwaggerModule montado en el puerto HTTP 3003. En usuario-service teníamos lo mismo y lo sacamos — porque no tiene sentido tener docs Swagger en un MS que eventualmente va a ser TCP-only.

    Por qué está mal: El Swagger documenta endpoints HTTP. Pero los endpoints de verdad (products.list, products.create, etc.) son TCP y Swagger no los ve. Lo único que documenta es el healthcheck. Aparte, el frontend no pega directo al puerto 3003 — todo pasa por el gateway. Swagger ahí es código muerto que después hay que limpiar.

    Cómo arreglarlo: Sacar SwaggerModule del main.ts y dejar el HTTP vivo solo para health (GET /health). Cuando cerrés el HTTP directo por completo, ya está.

    🟡 Mejoras IMPORTANTES (hay que resolver antes de mergear)

    ÍtemDetalle
    vendedorId ≠ sub del JWT

    Qué pasa: En tus TCP controllers usás user.sub ?? user.userId como vendedorId. En usuario-service, el sub del JWT es el authUserId (el ID del registro en AUTH_USER), NO el vendedor.id de la tabla VENDEDOR.

    Por qué está mal: Hay una relación 1:1 entre AUTH_USER y VENDEDOR, pero tienen IDs diferentes. usuario-service tiene un VendedorResolver que traduce un authUserId al vendedorId real. Si vos usás el sub directo, estás escribiendo el ID de auth en el campo vendedorId de tus productos — y ese ID no existe en la tabla VENDEDOR.

    Cómo arreglarlo: Tenés dos opciones:
    1. (Recomendada) Hacer una llamada TCP desde products-service a usuario-service para resolver el vendedorId real usando el VendedorResolver.
    2. (Simplificada) Si confirmamos que sub = vendedorId (porque el JWT se genera con el vendedorId), entonces está bien — pero hay que verificarlo con el equipo. Preguntar antes de asumir.
    Interceptores duplicados

    Qué pasa: Implementaste tus propias versiones de LoggingInterceptor, TimeoutInterceptor y TransformInterceptor. El proyecto ya tiene versiones estándar en usuario-service/src/common/interceptors/.

    Por qué está mal: Cuando un dev se mueve entre MS, espera el mismo comportamiento: mismo formato de log, mismo timeout, misma estructura de respuesta. Con interceptores propios, el products-service va a loguear distinto, responder distinto, y tener timeouts distintos al resto del sistema.

    Cómo arreglarlo: Copiar los interceptors de usuario-service o, mejor, extraerlos a @agua/contracts como librería compartida. Por ahora con copiarlos alcanza — después los unificamos.
    Sin docker-compose

    Qué pasa: No hay un service definido en docker-compose.yml para products-service. Si alguien hace docker compose up, tu MS no arranca.

    Por qué está mal: El stack completo se levanta con un solo comando. Si products-service no está en el compose, cada dev tiene que acordarse de levantarlo aparte, configurar las env vars manualmente, etc. Es insostenible en equipo.

    Cómo arreglarlo: Agregar al docker-compose.yml raíz un bloque similar a usuario-service:
    products-service: { build: context: ., dockerfile: MicroServices/products-service/Dockerfile, ports: ['3003:3003', '3013:3013'], env_file: ./MicroServices/products-service/.env, depends_on: [postgres, redis] }
    Sin .env.example

    Qué pasa: No hay un archivo .env.example en tu MS. Milagros sí lo tiene en entregas-service.

    Por qué está mal: Un dev nuevo (o vos mismo en 2 meses) no sabe qué variables de entorno necesita el servicio. Tiene que leer el código para descubrir que necesita DATABASE_URL, TCP_PORT, PORT, IVA_PORCENTAJE. Es una pérdida de tiempo al pedo.

    Cómo arreglarlo: Crear MicroServices/products-service/.env.example con:
    DATABASE_URL=postgresql://postgres:postgres@localhost:5433/agua
    PORT=3003
    TCP_PORT=3013
    IVA_PORCENTAJE=21
    TransformInterceptor envuelve TCP

    Qué pasa: Tu TransformInterceptor checkea context.getType() y si es HTTP transforma la respuesta. Pero el RpcExceptionFilter también maneja ambos contextos.

    Por qué está mal: No hay bug actual, pero si alguien toca el interceptor y no checkea el type, va a transformar respuestas TCP también. El usuario-service ya pasó por este problema y tiene la solución correcta.

    Cómo arreglarlo: No tocar nada ahora, pero cuando copies los interceptors de usuario-service esto ya viene resuelto.
