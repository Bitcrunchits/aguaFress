    🔄 TCP + Gateway

  • ✅ Transporte TCP configurado — puerto 3013, @MessagePattern en controllers, startAllMicroservices()
  • ✅ TcpPayloadAdapter — implementa requireUser(), requireRole(), validación con ValidationPipe. Mismo patrón que usuario-service.
  • ✅ vendedorId del JWT — los handlers de escritura usan el token, nunca el body. Correcto per regla de seguridad.
  • ✅ Ownership check — ProductsService. assertOwnership() en update/delete.
  • ❌ Faltan action registry entries — el gateway no tiene las 8 rutas de products-service. Sin eso, el gateway no sabe redirigir a este MS.
  • ❌ Falta ClientProxy en gateway — no está registrado el ClientsModule hacia products-service:3013.
  • ⚠️ Falta docker-compose entry — no hay service definido para products-service.
  • ⚠️ vendedorId = sub del JWT — asume que el sub es el vendedorId directo. En usuario-service hay un VendedorResolver que traduce authUserId → vendedor.id. Esto puede no matchear.

    • ⚠️ Swagger

  • ✅ Swagger solo en HTTP directo — seguro. Los TCP controllers usan @Controller() sin ruta HTTP, así que Swagger no intenta documentarlos. El crash que vimos antes era por @ApiExcludeController en el gateway con rutas dinámicas. Acá no aplica.
  • ✅ No hay @ApiExcludeController — correcto, acá no hace falta.

    • 🔴 Mejoras CRÍTICAS

    ÍtemDetalle
    Schema desunificado El proyecto usa un schema Prisma ÚNICO en usuario-service/prisma/schema.prisma. Las tablas productos, categorias, marcas deben estar ahí, no en un schema separado. Si no, las migraciones rompen.
    Sin action registry Las 8 rutas TCP de products-service no existen en el gateway. Sin eso, el gateway no sabe enrutar. Hay que agregar products.* y categories.* a MicroServices/gateway/src/actions/action-registry.ts.
    TCP sin ClientProxy El gateway necesita un ClientsModule.register() apuntando a products-service:3013 para poder enviarle mensajes TCP.
    Faltan tests Solo 1 spec (PricingService). Faltan tests de: ProductsService (CRUD, ownership, filtros), TCP controllers, RpcExceptionFilter, interceptors.
    Naming @@map inconsistente El proyecto usa UPPERCASE: @@map("USER"), @@map("DELIVERY"). products-service usa lowercase: @@map("productos"), @@map("categorias"), @@map("marcas"). Hay que unificar.

    🟡 Mejoras IMPORTANTES

    ÍtemDetalle
    vendedorId resolution El README ya lo advierte: asume que sub del JWT es el vendedorId. En usuario-service hay un VendedorResolver que traduce authUserId → vendedor.id. Si products-service necesita ese mismo mapeo, hay que resolverlo vía TCP a usuario-service.
    Interceptores duplicados LoggingInterceptor, TimeoutInterceptor, TransformInterceptor son implementaciones propias. El proyecto ya tiene versiones estándar en usuario-service. Hay que reemplazar por las del equipo para mantener consistencia.
    Sin docker-compose No hay entry de products-service en el docker-compose.yml raíz. No se puede levantar junto con el resto del stack.
    Sin .env.example Milagros sí lo tiene. Ayuda a que otros devs sepan qué variables necesita: DATABASE_URL, TCP_PORT, PORT, IVA_PORCENTAJE.
    TransformInterceptor envuelve TCP Evita type !== 'http' → return next.handle(). Pero el RpcExceptionFilter también maneja ambos contextos. Verificar que no haya doble transform.
