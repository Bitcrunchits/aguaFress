Flujo de trabajo con Pull Requests y sesiones de integración

1. Flujo de trabajo diario

⚠️ Regla de oro: Nunca codees directo en develop ni en main.

1.1 Crear una rama

$ git checkout develop && git pull $ git checkout -b nombre/apodo-descripcion # Ej: adrian/usuario-base, emiliano/productos-crud, agustin/ordenes-carrito

1.2 Codear y commitear

Commits atómicos con mensajes claros:

$ git add -A $ git commit -m "feat(auth): login con JWT" $ git commit -m "feat(users): CRUD de perfiles"
TipoCuándoEjemplo
featNueva funcionalidadfeat(orders): crear pedido desde carrito
fixCorrección de bugfix(products): precio sin IVA no se calculaba
refactorReestructuraciónrefactor(auth): extraer middleware JWT
docsDocumentacióndocs: actualizar guía de contratos
choreConfiguraciónchore: agregar Docker profile para entregas

1.3 Subir y crear PR

$ git push origin nombre/apodo-descripcion

Ir a GitHub → crear Pull Request a develop. En la descripción incluir:

  • 📌 Qué hace el PR
  • 🔗 Issue de Jira relacionado (ej: AG-12)
  • 🧪 Cómo probarlo (endpoints, payloads)
  • ⚠️ Breaking changes, si los hay

2.2 Criterios de aprobación

  • ✅ Compila sin errores (pnpm run build)
  • ✅ Endpoints funcionan (probado con Postman o Thunder Client)
  • ✅ No hay código comentado ni console.log sueltos
  • ✅ Los mensajes de commit siguen conventional commits
  • ✅ No rompe otros servicios (revisar que los contratos sigan vigentes)
💡 Si el PR toca packages/contracts/, TODOS los devs deben revisarlo.

2.3 Merge

Usar Squash & Merge para mantener el historial limpio. Un PR = un commit en develop.

3. Sesiones de integración

🎯 Objetivo: Detectar problemas de comunicación entre servicios. NO es para terminar código pendiente.

3.1 Periodicidad

  • Semana 2: Primera integración — solo levantar servicios + health check + Redis
  • Semanas 4-5: Integración con lógica de negocio parcial
  • Semanas 7-8: Integración completa del MVP
  • Ad-hoc: Cuando un PR toca contracts o eventos

3.2 Formato

PresencialRemoto
  • Host conecta proyector
  • Todos ven la misma pantalla
  • Host prueba endpoints mientras los otros observan
  • Host comparte pantalla (Discord/Zoom)
  • Host ngrok tuneliza localhost
  • Cada uno prueba desde su máquina contra la URL de ngrok

3.3 Qué hacer durante la sesión

  1. Host levanta todo: docker compose --profile all up --build
  2. Verificar health checks de todos los servicios
  3. Probar flujo completo: registro → login → crear producto → crear pedido
  4. Verificar que los eventos lleguen a Redis Streams
  5. Anotar TODO lo que falle (no arreglarlo en la sesión)
  6. Crear issues en Jira para cada problema detectado
⚠️ La sesión de integración NO es para arreglar código. Es para DETECTAR problemas. Cada uno arregla su servicio después en su rama.
