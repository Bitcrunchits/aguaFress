1. Contexto del Proyecto

AguaFress es una plataforma marketplace que conecta distribuidores de agua y soda con sus clientes. El modelo de negocio es por cartera: cada vendedor (distribuidor) maneja sus propios clientes, productos y pedidos, con aislamiento total entre vendedores.

1.1 Stack Tecnológico

ComponenteTecnología
BackendNode.js 22 + NestJS 10 + TypeScript 5
ORMPrisma 5
Base de datosPostgreSQL 15
Cache / Event BusRedis 7 con Streams
Package Managerpnpm 11.5 (monorepo)
AutenticaciónJWT + Passport + bcrypt

1.2 Los 3 Roles del Sistema

RolQué puede hacerEjemplo
super_adminVer todo, crear vendedores, activar/suspenderDueño de la plataforma
vendedorGestiona SUS clientes, productos, pedidosDistribuidor de agua
clienteSolo ve SU vendedor asignado, hace pedidosCliente final
⚠️ Principio importante
Aislamiento de cartera: un vendedor NO puede ver los clientes de otro vendedor. Un cliente NO puede ver otros vendedores. Cada query debe filtrar por la relación del usuario autenticado.

2.2 Patrón NestJS: Module → Controller → Service

NestJS organiza el código en módulos. Cada módulo agrupa controladores (HTTP) y servicios (lógica de negocio).

🔁 Flujo de una request
HTTP Request → Controller (valida input) → Service (reglas de negocio) → Prisma (base de datos) → Event (Redis Stream) → Response

2.3 Archivo main.ts — Bootstrap de NestJS

import { NestFactory } from '@nestjs/core';
import { ValidationPipe } from '@nestjs/common';
import { AppModule } from './app.module';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);

  app.setGlobalPrefix('api');

  app.useGlobalPipes(
    new ValidationPipe({
      whitelist: true,              // Elimina campos que no están en el DTO
      forbidNonWhitelisted: true,   // Error si mandan campos extra
      transform: true,              // Convierte strings a tipos (ej: "5" → 5)
    }),
  );

  const port = process.env.PORT || 3001;
  await app.listen(port);
}
bootstrap();
✅ Buenas prácticas aplicadas
whitelist: true + forbidNonWhitelisted: true evita que manden datos maliciosos. transform: true convierte automáticamente tipos (query params string → number).

3. Modelo de Datos — Prisma Schema

3.1 La Decisión Arquitectónica Más Importante

Problema original: los 3 roles (admin, vendedor, cliente) estaban en una sola tabla USER con 22 columnas, la mayoría nullable. Esto viola SRP (Single Responsibility): la misma tabla manejaba login + perfil de vendedor + perfil de cliente + relaciones.

❌ Tabla única — Antes (Anti-patrón)
model User {
  id          String    @id
  email       String    // login
  password    String    // login
  role        UserRole
  nombre      String?   // perfil
  apellido    String?   // perfil
  dni         String?   // SOLO cliente
  telefono    String?   // ambos
  empresa     String?   // SOLO vendedor
  logo        String?   // SOLO vendedor
  estado_vendedor VendedorEstado? // SOLO vendedor
  ciudad_default String?  // SOLO vendedor
  qr_token    String?   // SOLO vendedor
  // ... 22 columnas, 14 nullable
}

Problemas: columnas sin sentido para cada rol, validación compleja, riesgo de bugs, violación de SRP.

✅ Tablas separadas — Ahora (SRP)
// 1. Solo login
model AuthUser {
  id          String    @id
  email       String    @unique
  password    String
  role        UserRole
  is_active   Boolean
  is_verified Boolean
}

// 2. Solo vendedor
model Vendedor {
  id              String    @id
  auth_user_id    String    @unique  // FK → AuthUser
  nombre          String
  empresa         String?
  estado          VendedorEstado
  qr_token        String?   @unique
}

// 3. Solo cliente (con dirección completa)
model Cliente {
  id                String    @id
  auth_user_id      String    @unique  // FK → AuthUser
  nombre            String
  dni               String?
  tipo_factura      TipoFactura?
  direccion_calle   String?
  direccion_ciudad  String?
  direccion_cp      String?
  vendedor_id       String             // FK → Vendedor
}

// 4. Solo admin
model SuperAdmin {
  id           String  @id
  auth_user_id String  @unique  // FK → AuthUser
  nombre       String
}

// 5. Trazabilidad
model AuditLog {
  id         String  @id
  usuario_id String? // FK → AuthUser (quién)
  target_id  String? // FK → AuthUser (sobre quién)
  accion     String  // "profile.updated", "client.assigned"
  detalle    Json?   // diff de cambios
  ip         String?
}

Porque podemos consultar por ciudad (WHERE direccion_ciudad = 'Córdoba'), indexar campos, y mantener integridad referencial. Si fuera JSON, no podríamos filtrar eficientemente.

5. Flujo de Registro y Login (con código)

5.1 Registro de Cliente (desde link QR)

  1. El vendedor genera un QR de invitación
  2. El cliente escanea el QR y llega a un formulario de registro
  3. El frontend envía POST /api/auth/register con { email, password, nombre, role: "cliente", qrToken }
  4. El AuthService valida, hashea el password con bcrypt, y crea el AuthUser
  5. Según el role, crea el perfil correspondiente (Cliente)
  6. Si viene con qrToken, busca el QR y asigna el vendedor automáticamente
  7. Publica UserCreatedEvent en Redis Stream (auth-stream)
  8. Devuelve { user: { id, email, role } }

Código conceptual del servicio:

// auth.service.ts (estructura planeada)
async register(dto: RegisterRequest) {
  const hashedPassword = await bcrypt.hash(dto.password, 10);

  // 1. Crear AuthUser
  const authUser = await this.prisma.authUser.create({
    data: {
      email: dto.email,
      password: hashedPassword,
      role: dto.role,
    },
  });

  // 2. Crear perfil según rol
  if (dto.role === UserRole.VENDEDOR) {
    await this.prisma.vendedor.create({
      data: {
        authUserId: authUser.id,
        nombre: dto.nombre,
        estado: 'pendiente',  // requiere activación del admin
      },
    });
  } else if (dto.role === UserRole.CLIENTE) {
    // Buscar vendedor por qrToken
    const qr = await this.prisma.qrCode.findUnique({ where: { codigo: dto.qrToken } });
    await this.prisma.cliente.create({
      data: {
        authUserId: authUser.id,
        nombre: dto.nombre,
        vendedorId: qr?.vendedorId,
      },
    });
  }

  // 3. Publicar evento
  await this.redis.xAdd(RedisStreams.AUTH, '*', {
    data: JSON.stringify({
      type: 'UserCreated',
      userId: authUser.id,
      email: authUser.email,
      role: authUser.role,
    } satisfies UserCreatedEvent),
  });

  return { user: { id: authUser.id, email: authUser.email, role: authUser.role } };
}

5.2 Login

  1. El usuario envía POST /api/auth/login con { email, password }
  2. El AuthService busca el AuthUser por email
  3. Compara el password con bcrypt
  4. Si es válido, genera un JWT con @nestjs/jwt que incluye { sub: id, email, role }
  5. Genera un refreshToken (otro JWT con expiración más larga)
  6. Devuelve { token, refreshToken, user }
async login(dto: LoginRequest) {
  const user = await this.prisma.authUser.findUnique({ where: { email: dto.email } });
  if (!user) throw new UnauthorizedException('Credenciales inválidas');

  const passwordValid = await bcrypt.compare(dto.password, user.password);
  if (!passwordValid) throw new UnauthorizedException('Credenciales inválidas');

  if (!user.is_active) throw new UnauthorizedException('Cuenta desactivada');

  const payload = { sub: user.id, email: user.email, role: user.role };
  const token = this.jwtService.sign(payload, { expiresIn: '24h' });
  const refreshToken = this.jwtService.sign(payload, { expiresIn: '7d' });

  return { token, refreshToken, user: { id: user.id, email: user.email, role: user.role } };
}
🔐 Seguridad
  • bcrypt usa salt rounds = 10 (recomendado: 10-12)
  • JWT expira en 24h, refreshToken en 7d
  • userId NUNCA viene del body — se extrae del token JWT
  • Las contraseñas NUNCA se devuelven en respuestas

6.3 ¿Por qué Redis Streams y no RabbitMQ?

Redis StreamsRabbitMQ
ComplejidadBaja (Redis ya está en el stack)Alta (servidor nuevo)
Persistencia✅ Sí (redis streams son persistentes)✅ Sí
Consumer Groups✅ Sí✅ Sí
Mensajes fallidosSe manejan con pending entriesDead letter queue dedicada

✅ Decisión técnica
Como Redis ya está en el stack para caché, usar Redis Streams evita agregar otro servicio (RabbitMQ, Kafka). Para el volumen de MVP (cientos de pedidos/día, no millones), es más que suficiente.

7. Problemas Encontrados y Soluciones

Problema 1: Tabla única USER con 22 columnas nullable

Arquitectura Síntoma: muchos campos opcionales que solo aplican a un rol, validación compleja, riesgo de mezclar datos en queries.

Solución: Dividir en 4 tablas (AuthUser, Vendedor, Cliente, SuperAdmin). Cada tabla solo tiene los campos que necesita. Las relaciones 1:1 se manejan con @unique en la FK. Ver sección 3.1

Por qué funciona: SRP puro. AuthUser solo sabe de login. Vendedor solo sabe de vender. Cliente solo sabe de comprar. Si mañana cambia la lógica de login, no tocamos la tabla de vendedores.

Problema 2: Direcciones incompletas en Cliente

Modelo de datos Síntoma: la documentación requería ciudad, provincia, CP para la dirección de entrega, pero el schema original no los tenía. Tampoco tipoFactura.

Solución: Agregar 10 columnas de dirección estructurada a la tabla CLIENTE (calle, número, piso, referencia, barrio, ciudad, provincia, CP, latitud, longitud) más tipo_factura (enum B|C).

Alternativa descartada: guardar dirección como JSON. Se descartó porque no permite consultar por ciudad ni indexar.

Alternativa descartada v2: tabla separada DIRECCION. Se descartó porque en MVP el cliente tiene 1 sola dirección. Si en V2.0 necesita varias, se migra.

Problema 3: npm → pnpm — migración del monorepo

Tooling Síntoma: el proyecto usaba npm workspaces, que es lento, no tiene content-addressable store, y el node_modules pesaba mucho.

Solución: Migrar a pnpm 11.5. Crear pnpm-workspace.yaml, cambiar "@agua/contracts": "*" a "workspace:*", usar pnpm --filter en vez de npm -w.

Problema específico: pnpm bloquea los postinstall scripts por seguridad. Hubo que ejecutar pnpm approve-builds para prisma, bcrypt, nestjs/core.

Otro problema: pnpm ignora el campo "workspaces" de package.json. Requiere pnpm-workspace.yaml.

Problema 4: Names de relaciones inconsistentes en Prisma

Prisma Síntoma: al ejecutar prisma generate, Prisma tiraba error "CarteraVendedor is neither a built-in type, nor refers to another model".

Solución: El modelo Vendedor tenía cartera CarteraVendedor[] sin especificar que CarteraVendedor es el nombre de la relación (no un modelo). Se cambió a cartera Cartera[] @relation("CarteraVendedor").

Por qué pasa: En Prisma, las relaciones tienen dos partes: (1) el modelo destino y (2) el nombre de la relación (opcional, necesario si hay múltiples relaciones entre mismos modelos). Si ponés CarteraVendedor[] sin @relation(), Prisma busca un modelo llamado CarteraVendedor que no existe.

Problema 5: La migración de Prisma falla sin base de datos local

Entorno Síntoma: prisma migrate dev falla con P1001: Can't reach database server at localhost:5433.

Solución: La migración se ejecuta cuando el entorno Docker está levantado. Mientras tanto, prisma generate funciona sin base de datos porque solo genera el cliente TypeScript. En desarrollo, el flujo es:

docker compose --profile adrian up -d     # levanta PostgreSQL
pnpm --filter @agua/usuario-service exec prisma migrate dev
pnpm run dev                                # arranca el servicio

Problema 6: tsconfig paths para @agua/contracts

TypeScript Síntoma: los servicios importan de @agua/contracts pero es un workspace local, no está publicado en npm.

// tsconfig.json de usuario-service
"paths": {
  "@agua/contracts": ["../../packages/contracts/src"]
}

Solución: TypeScript resuelve la importación via paths + pnpm linkea el workspace con workspace:*. NestJS build lo resuelve automáticamente.

Problema 7: ¿Dónde van los logs de auditoría?

Arquitectura Síntoma: el notifications-service registra logs de sistema en MongoDB (eventos de dominio), pero no hay trazabilidad para acciones internas como "quién cambió el perfil de un usuario".

Solución: Dos niveles de log:

NivelDóndeQué registraBackend
Sistemanotifications-serviceEventos de dominio (UserCreated, OrderCreated)MongoDB
Auditoríausuario-serviceCambios internos (update profile, assign client, login attempts)PostgreSQL (tabla AUDIT_LOG)

La tabla AUDIT_LOG se creó en PostgreSQL del propio servicio. No necesita MongoDB. Se escribe con this.prisma.auditLog.create(...).

Problema 8: Eventos no documentados o inconsistentes

Documentación Síntoma: el evento DeliveryStatusChangedEvent existía en events.ts pero no estaba documentado. OrderConfirmed como evento separado no existía (se usa OrderStatusChanged con filtro de estado).

Solución: Sincronizar events.ts con la documentación. Usar union types por stream para que cada consumer solo vea los eventos que le interesan (ISP).

// Cada servicio importa solo su unión:
import type { UserEvent } from '@agua/contracts/events';
// ↑ SOLO ve VendedorStatusChanged y CarteraClienteAdded

8. Puntos Clave para la Presentación

🎯 Argumentos fuertes para defender
  1. SRP en el modelo de datos: "Dividimos la tabla USER en 4 porque cada rol tiene responsabilidades distintas. Si mañana cambia la lógica de login, no tocamos vendedores ni clientes."
  2. Validación en el pipe global: "Usamos ValidationPipe con whitelist + forbidNonWhitelisted. Esto evita que un atacante mande campos extra en el body."
  3. Contratos tipados: "Todos los microservicios comparten tipos desde @agua/contracts. Si alguien cambia un DTO, TypeScript lo detecta al compilar. No hay sorpresas en runtime."
  4. Aislamiento de cartera: "Cada vendedor solo ve sus clientes. Cada query incluye el filtro por vendedor_id. Es la regla de negocio más importante."
  5. Redis Streams vs RabbitMQ: "Elegimos Streams porque Redis ya estaba en el stack para caché. No necesitamos otro servidor. Para el volumen del MVP alcanza."
  6. pnpm: "Migramos de npm a pnpm. El node_modules se optimiza con content-addressable store, ocupa menos disco y las instalaciones son más rápidas."

8.1 Preguntas Frecuentes (preparate)

🤔 ¿Por qué no usaste MongoDB para las direcciones?

Porque la dirección del cliente necesita consultarse por ciudad (WHERE direccion_ciudad = 'Córdoba'). Con columnas estructuradas podemos indexar. Con JSON dentro de MongoDB, las consultas son más lentas y complejas.

🤔 ¿Por qué separar en tablas si después igual hacés joins?

Por SRP. La tabla única tiene 22 columnas, 14 nullable, y cada query tiene que filtrar por role para no mezclar vendedores con clientes. Con tablas separadas, cada consulta va a la tabla correcta directamente. Los joins son ocasionales (cuando necesitamos email + perfil).

🤔 ¿Por qué NestJS y no Express?

NestJS provee: inyección de dependencias, módulos, guards para auth, pipes para validación, interceptors. En Express tendríamos que construir todo eso manualmente. Para un proyecto con 6 microservicios, NestJS reduce mucho el boilerplate.

🤔 ¿Qué pasa si expira el JWT?

El JWT expira a las 24h. El frontend usa el refreshToken (7 días) para pedir uno nuevo sin que el usuario tenga que loguearse de nuevo. Si también expiró el refreshToken, tiene que hacer login otra vez.

🤔 ¿Cómo manejás errores de base de datos?

NestJS tiene Exception Filters globales. Prisma lanza excepciones tipadas (P2002 = unique constraint, P2025 = not found). Los capturamos y devolvemos un ErrorResponse estandarizado con statusCode, message y details.
