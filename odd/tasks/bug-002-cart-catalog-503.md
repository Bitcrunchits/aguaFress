# BUG-002 — cart catalog 503

## Objective

Replace the unconditional product-catalog 503 in orders-service with a scoped catalog read so authorized clients can add available products to carts and validate them at checkout. Keep product visibility, seller identity, and failure behavior consistent across products-service and orders-service. This is a NEW implementation plan: the prior worktree was lost, and its implementation and verification must not be treated as completed in this checkout.

## Current evidence

- `MicroServices/orders-service/src/common/common.module.ts` binds `PRODUCT_CATALOG_PORT` to `UnavailableProductCatalog`; its `getSnapshot` always rejects with 503. `CartService.addItem` reads the catalog before resolving or creating a cart; checkout also reads it.
- `products.get` in `MicroServices/products-service/src/tcp/products-tcp.controller.ts` requires `query.id` and scopes the result using authenticated `payload.user`; an unscoped internal read must not bypass that boundary.
- Products' cliente-to-vendedor resolver currently reads `providers[].vendedorId`, but usuario-service's `toProviderResponse` returns `providers[].id` from `relation.vendedor.id`. The resolver must map that domain seller ID, never JWT `userId`.
- Gateway dispatch defaults to a 5000 ms TCP timeout. An internal catalog request using the same 5000 ms budget risks the gateway timing out first, particularly when products-service performs another nested lookup. Timeout handling must be bounded and distinguish transport failures from business 404s.

## Scope and restrictions

- In scope for this authorized implementation: an orders-side `ProductCatalogPort` TCP adapter and dependency binding; authenticated client identity propagation through cart and checkout, including the async order path; the products-side cliente provider resolver mapping from `providers[].id`; focused unit tests and configuration/timeout checks.
- Preserve `userId` as JWT `AUTH_USER.id` and `vendedorId` as the domain `VENDEDOR.id`. Do not accept user identity from request bodies; use the authenticated TCP user. Preserve products-service's own authorization and 404 visibility rules. Validate catalog response shape before using price, stock, seller, or availability values; keep failed validation from creating or changing carts/orders.

## Acceptance conditions

- Authorized cliente with an active, visible, priced, in-stock product belonging to the selected `vendedorId` can add it to a cart and validate it at checkout without the unconditional catalog 503.
- Catalog queries retain the caller's authenticated identity and seller scope across cart and order creation (including the queued path); other clients' or sellers' products remain inaccessible as 404 where products-service scopes them.
- Missing/out-of-scope products produce a nonretryable 404; transport failure, malformed snapshot, or timeout produces an appropriate bounded unavailable/error result. No cart creation/item mutation/order creation follows a failed catalog or stock validation.
- Provider mapping uses the confirmed domain `VENDEDOR.id`, not the JWT subject or an invented response field. Unit tests prove the mapping and both authorized and denied access.
- Gateway and nested internal timeout budgets are explicitly checked to avoid a 5000 ms versus 5000 ms collision; no DB/container/runtime validation is claimed without authorization and execution.
