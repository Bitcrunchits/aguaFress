1. ¿Qué es un Monorepo?

Un monorepo es tener todos los servicios en un mismo repositorio de Git, pero cada uno en su propia carpeta, con su propio package.json, su propio tsconfig.json, su propio Dockerfile. Es decir: compartimos el repo, no el código.

aguaFress/ ← un solo repo en GitHub ├── packages/ │ └── contracts/ ← tipos compartidos (DTOs, eventos) ├── services/ │ ├── auth-service/ ← solo Lucas toca esto │ ├── user-service/ ← solo Lucas toca esto │ ├── products-service/ ← solo Emiliano toca esto │ ├── orders-service/ ← solo Adrián toca esto │ ├── entregas-service/ ← solo Milagros toca esto │ └── notifications-service/ ← solo Agustín toca esto ├── gateway/ ← al final ├── docker-compose.yml ← el compose con perfiles └── package.json ← workspaces
💡 Regla de oro: Cada persona toca SOLO su carpeta de servicio. Nunca toques la carpeta de otro. Si necesitás cambiar un contrato (packages/contracts/), hablalo con el equipo antes.

2. Estructura completa

2.1 Cada servicio tiene:

services/mi-servicio/ ├── src/ │ ├── main.ts │ ├── app.module.ts │ ├── controllers/ │ ├── services/ │ └── prisma/ ← schema + migrations ├── prisma/ │ └── schema.prisma ├── test/ ├── Dockerfile ├── package.json ← dependencias propias ├── tsconfig.json ← config propia ├── tsconfig.build.json └── .eslintrc.js ← config propia

2.2 Paquete de contratos:

packages/contracts/ ├── src/ │ ├── events.ts ← tipos de eventos Redis │ └── index.ts ← re-exporta todo ├── package.json ← name: "@agua/contracts" └── tsconfig.json
📘 Ejemplo de events.ts:
export interface UserCreatedEvent {
  userId: string;
  email: string;
  role: 'super_admin' | 'vendedor' | 'cliente';
  qrToken?: string; // si viene de link público
  timestamp: string;
}

3. Primeros pasos (solo una vez)

3.1 Clonar

$ git clone https://github.com/.../aguaFress.git $ cd aguaFress

3.2 Instalar todo (raíz)

$ npm install # Esto instala las dependencias de TODOS los servicios y paquetes

Esto funciona porque en la raíz tenemos package.json con:

{
  "workspaces": [
    "packages/*",
    "services/*",
    "gateway"
  ]
}

3.3 Setear el contrato en tu servicio

En el package.json de cada servicio:

{
  "dependencies": {
    "@agua/contracts": "*"
    ...
  }
}

Y en tu código importás:

// services/auth-service/src/algo.ts
import { UserCreatedEvent } from '@agua/contracts';

4. Flujo de trabajo diario

1
Parar todo lo que no uses

No dejes Postgres corriendo de otros proyectos. Usá los puertos del compose.

2
Abrí el repo en tu editor

Solo trabajás en services/tu-servicio/ y packages/contracts/ (si necesitás).

3
Levantá tu infra con Docker

Usás el perfil de tu servicio. Abajo la tabla completa.

4
Corré tu microservicio

En otra terminal, npm run start:dev dentro de services/tu-servicio/.

5
Codeá, probá, codeá

NestJS en modo dev recarga automáticamente al guardar. Probá con Postman/Thunder Client.

6
Hacé commit y pusheá

Siempre de tu rama, con commits claros. Después hacés PR a main.

6. Git — Cómo manejamos las ramas

⚠️ Esto es importante: Como somos 5 tocando archivos distintos (cada uno su carpeta), los conflictos de Git son casi imposibles mientras cada uno toque su servicio y no el de otro. El único archivo compartido es packages/contracts/. Si necesitás cambiarlo, avisá al equipo.

6.1 Ramas

main ├── lucas/auth-base ← Lucas ├── emiliano/products-base ← Emiliano ├── adrian/orders-base ← Adrián ├── milagros/entregas-base ← Milagros └── agustin/notifications-base ← Agustín

6.2 Flujo diario

# 1. Actualizar mi rama con lo último de main $ git checkout main $ git pull $ git checkout lucas/auth-base $ git merge main # 2. Codear, codear, codear... # 3. Commit (muchos commits chicos, no uno gigante) $ git add services/auth-service/ $ git commit -m "feat(auth): add login endpoint with JWT" # 4. Pushear $ git push origin lucas/auth-base

6.3 Pull Request a main

Cuando tu feature funciona y está probada, creás un PR desde tu rama a main. Alguien del equipo lo revisa (mínimo 1 persona).

✅ Buenas prácticas

  • Commits chicos y descriptivos
  • Un PR por feature
  • Comentá el PR: "agrega login con JWT y refresh token"
  • Pusheá seguido (no trabajés días sin pushear)

❌ Malas prácticas

  • Commits como "cambios", "fix", "update"
  • PR de 20 archivos de 3 servicios distintos
  • Tocar la carpeta de otro compañero
  • Mergear sin avisar

6.4 Formato de commits

Usamos conventional commits:

feat(auth): add Google OAuth login │ │ │ │ └── ámbito: qué servicio/modulo │ └── tipo: feat (nuevo), fix (arreglo), refactor, docs, test, chore
TipoCuándo usarloEjemplo
featNueva funcionalidadfeat(orders): add create order endpoint
fixBug corregidofix(products): stock validation on create
refactorCambio que no agrega ni arregla nadarefactor(auth): extract JWT middleware

7. Cómo se comunican los microservicios

7.1 Redis Streams (eventos asíncronos)

Cuando pasa algo importante en tu servicio (se crea un usuario, un pedido, etc.), publicás un evento en un stream de Redis. Otros servicios lo escuchan y reaccionan.

┌─────────────────┐ publica ┌───────────────┐ │ auth-service │────UserCreated────▶│ Redis │ │ (Lucas) │ │ Streams │ └─────────────────┘ └──────┬────────┘ │ escuchan │ ▼ ┌──────────────────────┐ │ user-service │ │ (Lucas) │ │ → crea perfil │ └──────────────────────┘

En NestJS se ve así:

// PUBLICAR (en tu servicio) @Injectable() export class EventPublisher { constructor(@Inject('REDIS') private redis: Redis) {} async publish(stream: string, event: string, data: object) { await this.redis.xAdd(stream, '*', { type: event, data: JSON.stringify(data), timestamp: new Date().toISOString() }); console.log(`📤 Published ${event} to ${stream}`); } } // USO await this.eventPublisher.publish('auth-stream', 'UserCreated', { userId: user.id, email: user.email, role: user.role, timestamp: new Date().toISOString() }); // ESCUCHAR (en otro servicio) @Injectable() export class EventListener implements OnModuleInit { constructor(@Inject('REDIS') private redis: Redis) {} async onModuleInit() { // Consumidor dedicado para user-service en el stream auth-stream while (true) { const results = await this.redis.xReadGroup( 'user-service-group', 'user-service-consumer', [{ key: 'auth-stream', id: '>' }], { COUNT: 10, BLOCK: 2000 } ); for (const result of results) { for (const msg of result.messages) { console.log(`📥 Received ${msg.message.type}`); await this.handleEvent(msg.message); } } } } }

7.3 TCP (síncrono, solo Gateway)

Cuando el Gateway necesite una respuesta inmediata (ej: validar un JWT), usa TCP de NestJS. Esto no lo tocan hasta que armemos el Gateway. Por ahora todos los endpoints los probás directamente contra tu servicio en su puerto (3001 a 3006).

8. @agua/contracts — El paquete compartido

Hay un paquete en packages/contracts/ que contiene TODOS los tipos que comparten los servicios. Esto existe para que NO haya diferencias entre lo que publica un servicio y lo que espera otro.

packages/contracts/src/ ├── index.ts ← re-exporta todo ├── enums.ts ← UserRole, OrderEstado, DeliveryEstado, RedisStreams... ├── events.ts ← interfaces de eventos Redis └── dto/ ├── auth.dto.ts ← login, register, google, refresh ├── user.dto.ts ← perfiles, cartera, QR, link público ├── products.dto.ts ← productos, marcas, categorías ├── orders.dto.ts ← carrito + pedidos ├── deliveries.dto.ts ← entregas └── notifications.dto.ts ← activity logs

8.1 Cómo se usa

En tu servicio, importás los tipos que necesitás:

// services/mi-servicio/src/algun-servicio.ts import { UserCreatedEvent, // tipo del evento que publicás o escuchás LoginRequest, // tipo del request de un endpoint OrderEstado, // enum con los estados del pedido RedisStreams // nombres de streams: auth-stream, orders-stream, etc. } from '@agua/contracts';

Para que funcione, tu servicio lo tiene como dependencia:

{
  "dependencies": {
    "@agua/contracts": "*",
    ...
  }
}

Como estamos en un monorepo con npm workspaces, npm install desde la raíz ya lo linkea automáticamente. No necesitás publicarlo a npm.

8.2 Ejemplo real: publicar un evento

// auth-service publica UserCreated import { UserCreatedEvent, RedisStreams } from '@agua/contracts'; const event: UserCreatedEvent = { userId: user.id, email: user.email, role: user.role, timestamp: new Date().toISOString(), }; await redis.xAdd(RedisStreams.AUTH, '*', { data: JSON.stringify(event) });

8.3 Ejemplo real: escuchar un evento

// user-service escucha UserCreated import { UserCreatedEvent } from '@agua/contracts'; async handleMessage(raw: string) { const event: UserCreatedEvent = JSON.parse(raw); console.log(event.userId); // ✅ TypeScript sabe que existe console.log(event.email); // ✅ existe // console.log(event.noExiste); // ❌ error de compilación }
💡 Tip: Si necesitás agregar un campo a un evento existente, hablalo con el equipo primero. Los contratos los mantenemos acá en la raíz. Cambiás el interface, build, push, y todos actualizan con git pull + npm install.

9. Cada dev en su servicio

Acá está lo que cada uno necesita saber específicamente de su servicio:

👤 Lucas — auth-service (3001) + user-service (3002)

auth-service: Prisma apunta a postgresql://postgres:postgres@localhost:5433/agua_auth
user-service: Prisma apunta a postgresql://postgres:postgres@localhost:5434/agua_users

Lo primero que hacés: El schema de Prisma con USER + SESSION + REFRESH_TOKEN, migration, y el endpoint POST /auth/login. Después el register de vendedor con estado pendiente.

Flujo crítico: Cuando se registra un cliente vía link público, auth-service recibe un campo qrToken extra en UserCreated → user-service detecta ese token y crea RELACION_CARTERA automática.

📦 Emiliano — products-service (3003)

Prisma apunta a postgresql://postgres:postgres@localhost:5435/agua_products

Lo primero que hacés: Schema con PRODUCTO, MARCA, CATEGORIA, PRODUCTO_IMAGEN. Migrations. CRUD de categorías y marcas. POST /products con carga básica.

Ojo: Los favoritos y descuentos son SOLO modelo. No los implementes (son FUTURE).

🛒 Adrián — orders-service (3004)

Prisma apunta a postgresql://postgres:postgres@localhost:5436/agua_orders

Lo primero que hacés: Schema con CART, CART_ITEM, ORDER, ORDER_ITEM, ORDER_HISTORY, FACTURA. Migrations. Endpoints del carrito primero (POST /cart/items, GET /cart, etc.). Después la creación de pedidos.

Ojo: Método de pago en MVP es solo contra_entrega. Review es FUTURE.

🚚 Milagros — entregas-service (3005)

Prisma apunta a postgresql://postgres:postgres@localhost:5437/agua_entregas

Lo primero que hacés: Crear el schema de ENTREGA desde 0. Migration. Endpoint GET /deliveries con filtro por fecha. Después el PATCH /deliveries/:id/status.

Flujo crítico: Escuchás el stream orders-stream → cuando llega OrderStatusChanged con estado confirmado, creás una ENTREGA con estado pendiente automáticamente.

📋 Agustín — notifications-service (3006)

MongoDB en mongodb://localhost:27017/agua_logs

Lo primero que hacés: Conexión a MongoDB con Mongoose. Definir schema de ACTIVITY_LOG. Escuchar TODOS los streams de Redis y guardar cada evento.

Después: GET /logs con filtros (servicio, acción, fechas). Solo admin puede acceder.

Paralelo: Investigación de frontend (Canva, wireframes, stack).

10. Integración — Cómo unimos todo

Cada 1 o 2 semanas hacemos una sesión de integración. No esperen al final para juntar todo porque va a ser un quilombo.

9.1 Pasos de la integración

1
Coordinamos día y hora — Todos en vivo (Discord/Zoom), cada uno con su compu.
2
Cada uno pushea su rama a GitHub — Todo lo que tenga, aunque no esté terminado.
3
Mergeamos ramas a main — En orden. Si hay conflictos, los resolvemos entre todos.
4
Levantamos todo — docker compose --profile all up --build y vemos qué funciona.
5
Probamos el flujo completo — Usuario se registra → login → ve catálogo → agrega al carrito → hace pedido → vendedor lo ve → entrega.
6
Anotamos lo que falla — Creamos issues en GitHub o lo dejamos en un documento compartido.
💡 Importante: La integración no es para que todo funcione perfecto. Es para encontrar los problemas temprano. Si algo no funciona, lo anotamos, lo arreglamos y volvemos a probar. Es normal.

11. Problemas comunes y cómo resolverlos

ProblemaCausaSolución
❌ Cannot find module @agua/contracts No corriste npm install en la raíz, o no linkeó bien el workspace. npm install desde la raíz.
❌ Puerto ocupado Ya tenés algo corriendo en 5433, 3001, etc. lsof -i :5433 y matá el proceso, o cambiá el puerto en el compose temporalmente.
❌ Docker no encuentra el perfil No pasaste --profile nombre Fijate que sea docker compose --profile lucas up (sin "lucas" no levanta nada).
❌ Migration de Prisma falla La base no existe o la URL está mal. Verificá que el contenedor de postgres esté vivo: docker ps. Verificá la URL en .env.
❌ Redis no conecta Redis no está corriendo o la config apunta a otro host. docker compose --profile tuperfil up y verificá localhost:6379.
❌ No recibo eventos de otro servicio Consumer group mal configurado o stream name incorrecto. Verificá en el código que el stream name coincida (ej: orders-stream ≠ order-stream).
❌ Conflictos de Git en package.json Dos personas cambiaron el mismo archivo. Solo pasa con packages/contracts/. Resolvelo entre los dos afectados antes de mergear.

12. Checklist — Primer día de código

Antes de escribir UNA línea de código, cada dev tiene que tener esto funcionando:

#TaskCheck
1Cloné el repo, corrí npm install en la raíz y no dio error⬜
2Corrí docker compose --profile miperfil up y Redis + mi DB están levantados⬜
3Creé mi proyecto NestJS en services/mi-servicio/ con Prisma⬜
4Configuré el schema de Prisma con la URL de mi base⬜
5Corrí npx prisma migrate dev y las tablas se crearon⬜
6Creé un endpoint de prueba GET /health que devuelve { status: "ok" }⬜
7Corrí el servicio y puedo pegarle con Postman/Thunder Client⬜
8Importé @agua/contracts en mi servicio y funciona⬜
9Configuré Redis y puedo publicar un evento de prueba⬜
10Hice mi primer commit y push a mi rama⬜
💡 Si llegaste al paso 10, ya estás listo para arrancar tu feature. Si algo falla antes, preguntá. No sigas si tenés dudas porque después arrastrás el problema.

13. Esto es normal en un equipo que arranca

✅ "No entiendo cómo funciona Redis Streams"
— Normal, es la primera vez. Preguntá y lo vemos juntos.

✅ "Mi Docker no levanta"
— Normal, a todos nos pasa. Compartí pantalla y lo resolvemos.

✅ "No me llegan los eventos de X servicio"
— Normal, los streams requieren nombres exactos. Verificamos.

✅ "Mi PR tiene conflictos"
— Normal, los resolvemos entre todos. No mergees solo si tenés dudas.

❌ Lo que NO queremos: Que alguien se quede 3 días trabado sin preguntar, o que mergee algo que rompe el repo de otro sin avisar. Preguntar no molesta. Romper el trabajo de otro sí.
